# Stack-chan 硬件路线评估

> 2026-10-26 需求调整：下文五短句唤醒相关项保留为历史风险；经用户同意已移入 [V2](v2-iteration-memo.md)，不再是 V1 的 A1/A2/B 准入门槛。V1 改验按钮开始连续聊天及聊天键／电源键区分，其余硬件评估条件不变。

评估日期：2026-10-24。对象为官方 **M5StackChan K151**；用户已同意以此型号评估，并允许“成品 + 本地小主机”作为备选。未采购、未烧录、未实机测量。本次是官方资料与部分构建源码审查，不是完整代码审计；上游分支会变化，复用前需固定提交与依赖版本。

## 1. 结论

**K151 具备自主开发与更换固件的路径，值得认真评估。尚不能保证单机满足 Jarvis 全部需求。** 开放程度与算力、内存、音频效果是不同问题。采购后也不只是填入豆包 Key 就能获得当前 PRD 的全部行为。

新的路线命名：**A 成品路线；B 自建路线**。A 分为 A1 成品单机和 A2 成品 + 本地专用主机；B 内部的普通 Linux 与 Jetson 路线分别叫 B-L、B-J，替代旧 PRD 中的 A、C，避免混淆。

建议先评估 A2 是否能明显减少机械工作，同时保留 B-L 作为可控基线。A1 是低硬件成本候选，但唤醒、音频和存储工程风险较高；不能只按售价排序。此为工程建议，尚未选定采购路线。

## 2. 社区、成品和固件不是同一个东西

| 项目 | 本次核实 | 对 Jarvis 的意义 |
| --- | --- | --- |
| [stack-chan/stack-chan](https://github.com/stack-chan/stack-chan) | 社区固件、MOD、结构与电路资料；仓库标注 Apache-2.0 | 可参考整体分层与机械设计，不代表所有同名成品完全兼容 |
| [社区固件说明](https://github.com/stack-chan/stack-chan/blob/develop/firmware/README.md) | 支持 K151 对应的 M5StackChan CoreS3；可源码构建，社区固件会替换出厂固件 | 可控制宿主固件，也可写 JS/TS MOD；不是只能修改厂商提供的几个参数 |
| [M5Stack 官方仓库](https://github.com/m5stack/StackChan) | 提供设备固件、遥控器、App 与服务器相关代码；注明公开更新可能晚于发布版本 | 需要确认设备出厂版本与公开源码对应关系，不能把所有组件都视为 Jarvis 的必要依赖 |
| [官方固件构建说明](https://github.com/m5stack/StackChan/tree/main/firmware) | 提供依赖拉取、ESP-IDF 构建和刷写路径 | 支持自行构建路线，但本次未实际编译验证 |
| [StackChan-BSP](https://github.com/m5stack/StackChan-BSP) | Arduino 板级支持包，标注 MIT | 可另写自主设备程序，不必完整继承厂商云端应用 |

“自主开发”在这里指掌握应用逻辑、接口与可刷写固件；不等于芯片无线栈、所有驱动、模型都必须自己重写。官方 [firmware/LICENSE](https://github.com/m5stack/StackChan/blob/main/firmware/LICENSE) 标注 MIT；具体依赖、模型、字体与素材需随复用文件核对，不能把某一仓库许可证套用到全生态。

官方固件的 [main/CMakeLists.txt](https://github.com/m5stack/StackChan/blob/main/firmware/main/CMakeLists.txt) 引入 xiaozhi-esp32 的音频、WebSocket、状态机和唤醒模块。**这是存在这些组件的证据，不是支持 Jarvis 五条英语短句、豆包直连或全双工体验达标的证据。** 官方仓库有服务器目录，也不代表我们的架构必须租服务器；设备直连能力需单独验证。

## 3. 成品硬件与原需求的差异

K151 使用 ESP32-S3（240 MHz 双核、16 MB Flash、8 MB PSRAM），带 2 英寸屏幕、双麦克风、扬声器、microSD、两轴反馈舵机、Wi-Fi、摄像头和电池。[官方产品仓库](https://github.com/m5stack/StackChan)

官方规格还列出 Grove 扩展接口；出厂操作为短按开机、长按 6 秒关机。[产品手册](https://docs.m5stack.com/en/StackChan)

以下为针对 Jarvis 的工程判断，并非厂商承诺：

| Jarvis 要求 | A1 成品单机 | A2 成品 + 本地专用主机 |
| --- | --- | --- |
| 主要程序与 Skill 运行于 Linux | MCU 固件环境，需要另行确认平台变更；现有 Node 页面不能直接当固件烧入 | Linux 主机承担智能层，设备承担交互；需开发通信适配 |
| 五条本地英语唤醒 | 所选嵌入式引擎能否支持全部词句、内存是否足够，均未验证 | 可在主机检测，但需设备持续传输到本地的音频通路；不等于上传云端，也不是已具备能力 |
| 直接插话、立即停播 | 收音、播放、回声处理与算力需一起测 | 主机算力更宽裕；设备侧回声、网络缓冲和停播确认仍需测，不能自动视为解决 |
| 完整文字历史、三层记忆、待处理提炼 | 可研究 SD 存储与轻量索引；不是 8 MB 内存就绝对不能做，也不是有 SD 就已完成 | 主机持久化较贴近原方案；重连不得重复提炼或恢复旧回答 |
| 模式 Skill | 可移植提示词和行为规则；社区 MOD 不等同于 Jarvis Skill | 主机加载 Skill，终端暴露表情和动作能力 |
| 眼睛 + 一两行字幕 | 2 英寸屏需验证 20–50 cm 可读性；与约 8×8 cm 目标不同 | 同样受成品屏幕限制 |
| 短按启用/保存关机循环 | 原厂长按行为不符合，需验证按键事件与电源管理可改范围 | 还要处理一个按钮如何控制两台设备的生命周期；逻辑待机不能冒充系统关机 |
| 不依赖日常电脑、不租服务器 | 设备若能直连所需云 API 才可满足 | 需专用本地主机；Mac 仅用于开发，不能免费隐藏为交付依赖 |
| 摄像头、电池 | 成品自带；若选 A，建议允许硬件存在，V1 不启用视觉、不增加续航验收，待路线确认 | 同左；不是自动扩展 V1 视觉范围 |
| 后续 NVIDIA 扩展 | 可研究局域网增加计算节点，不是内置显卡升级；原有有线连接预留尚不成立 | 在专用主机侧保留连接能力；新增 Jetson 预算仍按原约定处理 |

A2 不假定 K151 是即插即用的 USB 声卡。双向音频、设备控制、断线重连与帧格式须从串口或局域网传输方案中验证选择。

## 5. B 路线值得参考什么

| 参考资源 | 可借鉴内容 | 复用边界 |
| --- | --- | --- |
| [社区 API](https://github.com/stack-chan/stack-chan/blob/develop/firmware/docs/api.md) | face、motion、audio、input 分离；可选设备能力；资源生命周期 | 在 Linux 侧借鉴接口责任，不照搬 Moddable/Piu 运行时；取消仍须按 Jarvis 轮次设计 |
| [MOD 与示例](https://github.com/stack-chan/stack-chan/blob/develop/firmware/mods/README.md) | 头部转向、设备自检、网络音频和应用层隔离的学习入口 | 示例未逐个实机验证；MOD ≠ 四种对话模式的现成实现 |
| [结构与装配资料](https://github.com/stack-chan/stack-chan/tree/develop/case) | 两轴布置、模块固定、STEP/STL、舵机中位与安装顺序 | 区分 v0/v1、舵机型号与成品结构；不能将小型结构直接放大承载 Linux 主机和大屏 |
| [BSP](https://github.com/m5stack/StackChan-BSP) | 成品外设驱动和板级自检方向 | 直接复用只适用于匹配硬件；别的主控需移植或重写驱动 |

所以 B 不需要把驱动、CAD、表情框架全部从零编写。适合自主开发的是 Jarvis 会话、记忆、Skill 和适配层，能复用的成熟模块先验证后复用。

为 V2 外壳减少返工，建议从 V1 就维护部件尺寸、重量、安装孔、接口朝向、散热和运动空间；重部件放底座，头部仅放必要器件；使用可拆连接和集中走线。V1 不新增外壳设计交付，也不承诺任意硬件升级都能装进同一外壳。

## 6. 决策门槛与主线隔离

1. **桌面资料门槛：** 明确 K151 版本、恢复刷机路径、软件许可、五词引擎候选、音频接口与关机路径。未通过不以低价直接推荐购买。
2. **A1 原型门槛：** MCU 上实际支持五词、打断、直连服务和 SD 历史；记录峰值内存与长期运行；不达标再比较 A2/B。
3. **A2 原型门槛：** 本地链路能够稳定收发音频、取消旧轮次、断线降级、驱动两轴；成本包含专用主机与电源；双设备按钮方案有证据。
4. **需求变更门槛：** 屏幕、Linux 部署、既有摄像头/电池、按钮、NVIDIA 连接方式若有变化，形成明确差异表后由用户选择路线；不默认删除需求。
5. **B 结构门槛：** BOM 之前做尺寸和重量布局草图，避免买完全部模块才发现无法装配或封装。

硬件评估作为 P1 独立事项推进；Mac 上的豆包接入、文本/记忆契约、轮次取消与表情事件继续复用。主控确定前不把 Linux 专有库或 ESP32 专有接口写进对话业务层。P1 仍以 2026-11-05 为决策检查点，若硬件验证未完成，如实记录风险与下一步，不据此停止语音主线或宣布路线已通过。
