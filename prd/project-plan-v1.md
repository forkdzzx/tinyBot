## 1. 执行原则与前提

- 2026-10-24 加入 Stack-chan 成品评估：A1 成品单机、A2 成品加专用本地主机，与 B 自建比较；B-L/B-J 仅为 B 内部主控分支。报告见 [Stack-chan 评估](stackchan-review.md)。硬件分支不阻塞 Mac 语音主线。
- 当前进入 P1，先验证高风险环节，再确定主控、音频链路、控制板和结构。用户已选择先用当前 Mac，硬件后续采购；火山引擎服务已开通并有真人试聊记录。2026-10-26 已完成记忆／模式与工具接口的最小验证；直接提示更新未通过，采用本地状态与工具路径。2026-10-27 最小历史／持久记忆闭环已提前接入，接着完善检索和冲突确认，见[实现记录](../docs/memory-implementation-2026-10-27.md)。
- 不预先锁定成品 A／自建 B、B 内部主控、具体硬件型号、编程语言或端到端／分模块语音路线。
- 先做能说话的最小系统，再让它有连贯的表情与动作，随后接入记忆和模式，最后优化日常体验。
- 机械、音频和电源验证前置；第 8–9 周是整体装配，不是第一次开始检查舵机或开关机。
- 计划假设用户可在工作之余稳定安排装配与体验时间，初始按每周约 6–10 小时预留，其中至少一次连续 2–3 小时的硬件调试时段。这是排期假设，尚未确认，不是对用户的既定要求。
- 到货和加工时间暂按 1–2 周预留作为排期假设，以采购时实际交期为准。等待硬件时推进模拟设备、状态机和配置工作。
- 我在对话授权范围内负责分析、文档、代码与可执行验证；采购付款、接线装配、设备刷写和现场体验主要由用户操作。没有连接真实设备时，不把模拟结果称为实机通过。
- 软件开发可在现有电脑上起步；第 3–4 周前需在目标 Linux 主控验证核心链路，避免后期才暴露平台不兼容。

## 4. 方案决策与采购顺序

| 决策点 | 何时 | 决策依据 | 本计划预设处理 |
| --- | --- | --- | --- |
| G0：需求基线 | T0 之前 | 用户确认 PRD 与审查建议 | 此后变更记录对范围、时间和成本的影响 |
| G1：技术路线 | W2 结束前争取完成 | 语音与打断原型、按钮会话、Linux 兼容性、BOM 和电源流程 | 先比较 A1/A2/B 的成本与需求差异；选 B 时再按预算优先 B-J、否则 B-L；不得削弱必需交互来迁就某块板 |
| G2：结构定型 | 最晚 W4–5，条件成熟可提前 | 真实屏幕尺寸与重量、单轴试验、线材和承重 | 再确定最终支架／加工件，不先按外观图盲目加工 |
| G3：功能冻结 | W9 结束 | 已确认功能完成集成，剩余主要是体验与可靠性问题 | 后三周聚焦修复，新功能记入后续版本 |
| G4：交付确认 | W12 至截止日 | 功能用例、主观体验、预算和已知限制 | 用户确认最终结果；未达标项明确处理，不静默删需求 |

采购按实际依赖分批：先购必须的验证模块；技术路线成立后购买主控、显示、音频和控制板；测得负载后确定最终执行器及结构件；最后补备件与理线固定材料。单关节验证件可以提前采购。所有验证和返工支出都应记账，不把试错成本藏在整机预算之外。

用户负责选择最终购买渠道与付款；我负责整理清单、兼容性、接线要求和替代项。现阶段没有采购授权执行或付款动作。

建议每周一次集中回顾：本周完成什么、有什么实测证据、还有哪些阻塞、下周需准备什么。阶段末另做一次演示。此节奏是协作建议，不创建定时提醒或后台自动任务。

建议使用一个简短的问题清单管理进度，至少记录：问题描述、影响、复现条件、日志／照片、本周处理人、状态与下一步。物理问题用实测资料定位，不凭软件日志断言硬件正常。

## 6. 关键依赖与风险应对

关键依赖链：**需求确认 → 音频／云服务／主控可行性 → 核心硬件到位 → 实机连续对话 → 全功能整合 → 稳定性与主观验收**。结构链同时推进：**屏幕与重量 → 单轴验证 → 支架加工 → 两轴装配 → 联调**。

| 风险 | 尽早发现的时间 | 对策 |
| --- | --- | --- |
| 选定语音服务无法满足打断、文字回传或记忆接入 | W1–2 | 用最小原型验证；必要时更换服务或采用分模块链路 |
| 本地多短句唤醒不稳定 | 已确认延期至 V2 | V1 用按钮开始连续会话，Hi Jarvis 仅为实验；保留失败证据与原验收，不继续占用 V1 关键路径 |
| 成品 MCU 或 A2 本地音频链路不满足体验 | W1–2 资料与最小原型 | 核对固件、按钮会话、收放音、SD 和电源按钮；A2 不假定 USB 声卡能力，不隐藏专用主机费用；不通过则保留 B 路线 |
| 自身外放导致误识别／无法插话 | W1–4 | 优先检查音频链路、回声处理和安装；必要时调整音频器件 |
| B-J 超预算、缺货或驱动不合适 | W1–2 | 按已确认规则选择 B-L，未来追加 Jetson 预算；实报交期 |
| 同一按钮无法覆盖主控关机后再开机 | W1–2 | 提前画电源状态与控制路径，验证必要电路；不只写应用层按钮处理 |
| 头部过重、结构晃动、走线干涉 | W2–5 | 先负载和单轴试验再加工，保留必要返工窗口 |
| 外设失联拖死整机 | W3–9 | 有界超时、独立降级和过期动作丢弃，按模块自检 |
| 记忆把推测当事实 | W5–6 | 记录来源与状态，用冲突案例验收，必要时调整提炼规则 |
| 时间不足或零件交期拖延 | 每周检查 | 先保持必需能力；精美外观、复杂动画等不扩大；必需项受影响时提出明确排期调整 |

## 7. 预算管理与交付清单

硬件预算沿用 PRD 的 5000 元整机上限，月云服务费用以 1000 元以内为目标。本计划不提供新的采购报价，也不改变 PRD 中尚需核实的 B-L／B-J 预算测算。

计划初期核实完整 BOM，中期记录实际支出，W10–11 以实际用量外推云服务月费。预算包含配件、线材、加工和必要试错，允许在原有预算分项间调整，但总额变化需明确报告。

最终交付应包括：

1. 能独立运行的 Jarvis 第一代整机及对应软件版本。
2. 实际 BOM、连接说明、关节标定参数和安装照片／说明。
3. 四种模式 Skill、配置示例、按钮会话使用说明；Hi Jarvis 实验入口若启用，单列本地资源与已知限制，五短句正式交付延期至 V2。
4. 历史、记忆与日志保存路径，以及人工备份恢复步骤。
5. 启动、使用、关机、更新和常见故障排查说明。
6. 对照 PRD 的验收记录、用户主观反馈、实测延迟与费用估算。
7. 已知问题、后续优化清单和明确未实现的范围。

项目已启动，按 P1 推进。阶段完成以验证记录为准；不会因日历进入下一周而自动标记完成。
