## 1. 产品定位与目标

Jarvis 是放在家中书房桌面的个人 AI 对话机器人。通过语音、眼睛表情和两个运动关节，提供查询、思考辅助与陪伴。它具备本地处理器和存储，使用云端模型完成主要智能能力，本地积累对话历史与个人记忆。

价值优先级：帮助查询和思考 > 陪伴聊天 > 提醒 > 安排事务。第一代实现前两项及事项记忆，不实现定时提醒和事务执行。

相较手机语音 AI，核心差异是实体存在感：能看见它倾听、思考、开心或困倦，并在适当时机点头和左右转动。第一代以日常可用为目标，允许裸露机械结构，不以精致外观作为交付条件。

### 1.1 使用者与环境

| 维度 | 已确认条件 |
| --- | --- |
| 使用者 | 产品所有者本人为主要使用者；不识别身份，不区分访客，所有对话使用同一份个人记忆 |
| 环境 | 中国境内普通家庭 Wi-Fi，家中书房，通常安静，通常只有一人 |
| 距离 | 人与机器人相距约 20–50 cm |
| 游戏／比赛声音 | 用户戴耳机，不要求处理电脑外放的游戏或比赛声音 |
| 机器人音频 | 麦克风收音，机器人自己的扬声器播放回答；仍需处理自身扬声器对麦克风的影响 |
| 使用时长 | 每天开机约 2–3 小时，实际聊天约 1–1.5 小时 |
| 供电 | 长期插电，第一代无电池 |
| 能力背景 | 用户有 Java 工作经验、树莓派及单片机经验、基础焊接经验，无机械设计经验，目前无专用制板工具 |
| 硬件预算 | 单台整机不超过 5000 元，含电源、存储、音频、电机、支架、加工等 |
| 云服务预算 | 每月 1000 元以内为预算目标，不是达到后强制停服的硬上限 |
| 时间 | 从 PRD v1.1 确认日开始三个月 |

### 1.2 成功定义

第一次完成“听到问题—理解—回答—外放”是项目第一个成功里程碑。第一代最终交付还应完成连续交流、记忆、模式、表情动作、主动搭话和异常恢复。

用户的主观感受是最终验收的重要依据：能跟上话题、不反复答非所问、不需要一直等候、不机械重复套话，愿意持续使用。第 12 节的数字用于发现问题和记录改进，不替代实际体验。

### 1.3 创作动机与参考边界

用户在大学期间于 2022 年看到 ElectronBot，形成了制作个人桌面机器人的愿望；目前希望结合大模型实现 Jarvis。这个背景意味着，“看起来在听我说话、会回应我的实体伙伴”是核心体验，不应在能完成 API 问答后才作为可有可无的装饰处理。

**ElectronBot review 建议：** 继承眼睛、姿态和表达节奏的协调方式；第一代不照搬六自由度、双臂、极限小型化、全部定制 PCB 或完整 Unity 编辑器。仍按两个关节、独立主控、可无正式外壳的既定范围实现。表达质量通过场景体验验收，不以动作数量和外形复刻程度验收。

### 2.3 场景与体验结果

| 场景 | 用户行为 | Jarvis 应有表现 |
| --- | --- | --- |
| 工作问答 | 口头询问 Java 或其他简单技术问题 | 尽快给出相关、简短解释，必要时搜索；无需粘贴代码 |
| 长时间专注 | 工作或游戏中 15–20 分钟未与 Jarvis 交流 | 非勿扰时主动说一句；无回应不继续打扰 |
| 游戏／看球陪伴 | 用户口述游戏进展、球场事件或询问比分 | 基于口述接话，按需查信息，不声称亲眼看到画面 |
| 英语练习 | 请求练口语，或明确进入英语练习话题 | 简单英文问题逐步引导，允许中文求助，先交流再纠正 |
| 跨会话交流 | 下次聊到同一个项目、偏好或球队 | 调用相关记忆，不把全部旧对话重新灌入当前上下文 |
| 临时不想聊天 | 用户说“别打扰我” | 停止主动搭话，仍可按聊天按钮发起对话 |

## 3. 电源、会话与主动交互

### 3.1 单按钮流程

这是已确认的有意设计：系统启动和启用交互是两个步骤，包括关机后重新启动。

```text
接通电源
  → 系统启动：屏幕关闭，不监听唤醒词，不主动搭话
  → 按一下电源按钮：显示眼睛，启用聊天入口和主动搭话规则（不自动连接云端）
  → 再按一下按钮：立即停止交互，保存必要数据，完成系统关机
  → 再按一下按钮：系统启动，屏幕关闭，不监听唤醒词
  → 再按一下按钮：显示眼睛，启用交互
  → 循环
```

不通过长短按区分功能，不额外要求确认关机。关机不是突然切断运行中的主控电源；主控关机后的再次开机需要硬件电源控制支持，必须在选型阶段验证。外接小控制板／电源控制电路可维持必要的按键检测，主控此时应已关机。

启动及关机进行中建议屏蔽重复按键触发；就绪前不重复执行开关机。启动时间和具体电路不在本 PRD 中承诺。

2026-10-26 工程衔接：上述单按钮指电源控制；“开始聊天”是独立的会话操作，不复用运行中按一下即关机的电源键。Mac 阶段使用测试页按钮；实体阶段优先复用设备独立用户按键，必要时增加简单会话按键，接线和成本纳入 BOM。具体器件在硬件选型时确定，不增加长短按规则或产品管理网页。

### 3.2 运行状态

| 状态 | 屏幕 | 语音处理 | 离开条件 |
| --- | --- | --- | --- |
| 已启动但未启用 | 关闭 | 不监听唤醒词，不上传环境声音 | 按键启用交互 |
| 交互待机 | 眼睛动画，空闲后困倦 | 默认不收音、不上传；显式启用实验入口时仅本地检测 `Hi Jarvis` | 聊天按钮、实验唤醒、主动搭话、电源按钮关机 |
| 会话中 | 倾听／思考／说话表情与简短文字 | 直接说话即可；需要时向云端发送语音 | 超时、明确结束、暂停等待、关机 |
| 延长等待 | 安静的倾听状态 | 保持倾听，支持用户继续交流；不主动开口 | 用户开口或 10 分钟到期 |
| 主动搭话等待 | 表达邀请／倾听 | 允许直接回应，30 秒应答窗口内可上传回应语音 | 有效回应进入会话；无回应回待机并抑制再次搭话 |
| 关机中／已关机 | 停止常规交互，关机完成后关闭 | 停止交互和上传 | 关机完成后按键重新启动 |

勿扰、当前模式、主动搭话抑制标记是独立状态属性，不应混为一个模式。网络或硬件故障可叠加在运行状态上。

### 3.3 开始聊天与会话结束

- 产品名固定为 **Jarvis**。V1 必备入口为“开始聊天”按钮：每次会话按一次，进入会话后直接说话，不需要每轮按键或持续按住按钮。
- 待机不自动连接语音云服务。用户按聊天按钮后允许建立会话并上传该次会话语音；页面明确提示正在连接和可以讲话，失败时显示原因并可重试。
- `Hi Jarvis` 保留为显式开启、可随时关闭的本地实验入口；默认关闭，不承诺成功率，不阻塞 V1 验收。未启用该实验入口时不加载唤醒模型；识别失败不影响按钮开始聊天。
- 其余四条短句及稳定本地唤醒移入 [V2 迭代优化备忘录](v2-iteration-memo.md)。当前页面与运行词表只开放 `Hi Jarvis` 实验入口，历史五短句列表和离线实验代码保留，不计为 V1 已交付能力。
- 按钮与实验唤醒都进入同一会话流程，不默认切换模式或触发专属回复。会话内无需重复触发。
- 默认从机器人最后一句播报结束、且用户没有继续说话时开始计算两分钟沉默。
- 用户继续说话后不因旧计时器结束会话；搜索、正常回答生成和播报过程中不错误触发沉默超时。
- 用户明确说“结束聊天”“停止聊天”等语义时结束当前会话，之后仍允许按空闲规则主动搭话。
- 用户说“等一下，我想想”时进入最多 10 分钟延长等待；一开口立即恢复交流，超时则结束会话。期间禁止主动搭话。
- 为补齐未回答边界，建议会话就绪后用户一直未说话时从就绪起计算两分钟；被打断后未形成有效新输入时，从停止播报起计算。
- 结束会话后保留眼睛动画；默认关闭该次麦克风与云连接，下次按聊天按钮开始。实验唤醒启用时可返回本地监听；空闲后困倦不应禁用聊天入口。
- 困倦表情初始建议在空闲 5 分钟后出现，可通过配置调整；此阈值不是需求澄清中指定的硬指标。

### 3.4 主动搭话

1. 交互启用后，即使还没聊过天，也允许在空闲 15–20 分钟后主动搭话。
2. 间隔在 15–20 分钟内随机选择；正常会话后从最后一次交流结束计算。建议每个空闲周期只抽取一次间隔。
3. 会话中、机器人播报中、用户说话中、延长等待中、勿扰、未启用交互或关机时不触发。
4. 一次只发起简短邀请，例如问是否在忙、是否想聊两句；不声称知道用户正在做什么，不假装看见游戏／比赛。
5. 用户可直接回答，不必再次喊唤醒词；有效回应进入正常会话。
6. 邀请播报结束后等待 30 秒。无有效回应则停止本次邀请，并禁止继续周期性搭话，直到用户再次主动发起交流。
7. 用户再次主动交流后恢复后续搭话资格；结束本次交流后重新计时。
8. 不做在场判断，接受偶尔对空房间发起一次搭话。
9. 工程补充：异常断网期间不发起依赖云端的邀请，不把未发出的邀请累积为待播报队列；恢复网络后不补发一串邀请。

### 3.5 勿扰

- “我先工作，别打扰我”等表达开启勿扰，只禁止主动发起闲聊，不禁止用户请求的会话或英语练习中的正常提问。
- 只有明确允许重新主动聊天，或系统重启，才解除勿扰。
- 按钮开始聊天、实验唤醒、结束一次会话、自动或手动切换模式都不解除勿扰。
- 建议解除后重新开始 15–20 分钟计时；若此前因无回应而抑制搭话，用户明确允许主动交流可同时解除该抑制。
- 重启恢复日常模式、关闭勿扰；交互仍需按键启用。建议同时重置主动搭话抑制与临时模式锁。

## 4. 语音对话与搜索

### 4.1 对话风格

- 理性、幽默、略带吐槽，关系定位为助手和朋友。
- 默认中文夹少量英文，使用自然人声；音色和语速可通过本地配置调整。
- 默认中短句，避免冗长句子、无关延伸和长篇播报；用户明确要求详细说明时可以展开。
- 游戏中可以适度吐槽，工作受挫时减少玩笑；允许有依据地反驳，不装作全知。
- 无把握时可先给简短推测，并清楚表达不确定，再让用户决定是否深入。实时比分等动态事实无法查证时不能猜测并冒充结果。
- 若没理解用户意思，应围绕关键歧义简短澄清，避免连续给出偏题长答案。

### 4.2 语音输入、判停与打断

- 通过聊天按钮进入会话；可选实验唤醒只在本地处理。只有用户启动会话或进入主动邀请应答窗口后才发送相关语音到云端，不为绕过本地识别而持续上传待机声音。
- 原始录音默认不保存；允许处理所需的短时内存缓冲，不将其作为录音文件长期留存。
- 普通交流优先快速接话，不强制用户说结束口令；“我说完了”若出现，应作为明确句末信号。
- 英语或技术表达停顿较多时，判停参数需实测调优，避免为追求速度频繁抢话。
- 用户直接插话时立即中断当前音频播放并处理新内容，无需先喊名字。
- 被中断的旧回答不自动续播；用户说“继续刚才的”时再根据当前上下文续讲。
- 播放队列中的旧音频应丢弃或失效，防止新问题后又冒出旧回答。
- **ElectronBot review 建议：** 打断时同步取消旧轮次尚未执行的动作、字幕及表情事件；实际关节平滑减速或保持，眼睛及时转为倾听。迟到的旧轮次结果不能重新触发已经取消的表达，详见 7.4。
- 机器人自身扬声器不能持续触发自我识别、自我打断或唤醒；回声处理是本期语音方案的验证重点。
- 听不清时直接请用户重说。连续两次无法识别有效内容后提示一次回到待机，不无限追问；可正常理解的回答重置失败计数。

### 4.3 等待反馈与字幕

- 需要明显等待时，可说一句简短、变化的“我查一下”等表达，再呈现思考眼睛；可配合短提示音。
- 不要求每轮固定播报“好的”“让我想想”；快速能答的问题直接回答。
- 屏幕保留眼睛，下方一两行辅助文字：识别结果、当前回答片段或必要的设备状态。
- 长文本简单分段更新即可，不做复杂滚动历史、全文浏览或代码排版。
- 屏幕识别结果用于辅助确认代码术语、人名、英文等；不额外引入复杂屏幕编辑流程。
- 工程建议：故障状态文字优先于普通字幕；正常状态恢复后自动回到当前交互显示。

### 4.4 联网搜索

- 按需搜索，不逐次征求许可，不要求用户查看来源链接。
- 时效性问题、赛事比分、需要核实的技术信息可触发搜索；普通闲聊不无谓调用。
- 比赛信息仅在用户询问时查询，不后台定期轮询，不做自动进球推送。
- 机器人不知道比赛画面和游戏屏幕内容，相关交流以用户口述及实际查到的信息为依据。
- 搜索异步进行，不锁死收音、打断和新问题处理。
- 新问题优先；旧搜索结果不突然插入正在进行的新回答。仍然相关或用户追问时才使用。
- 复杂搜索允许先简短回应，再在约 10–20 秒内给出结果；搜索超过 20 秒时简短说明暂时未查到并结束该轮等待，不能一直挂起。
- 对生成、搜索、语音合成等外部服务均需有超时和失败反馈，避免没有搜索时仍无限“思考”；具体非搜索超时初值在技术阶段确定。
- 搜索结果中涉及实时比分时应保留必要的时间语境；不把过时结果说成刚发生的事实。
- 可在本地诊断日志保留查询耗时、结果来源等必要信息，第一代不开发来源展示界面。

## 5. 模式与 Skill

### 5.1 四种内置模式

| 模式 | 主要行为 | 主动性与限制 |
| --- | --- | --- |
| 日常 | 查询、思考辅助、朋友式闲聊 | 按统一主动搭话规则运行 |
| 工作 | 简单技术问答、解释概念、协助思考 | 仍允许闲聊；只有明确勿扰才禁止主动搭话 |
| 陪伴 | 游戏与看球合并；接住用户口述，适度幽默 | 比分按需搜索，不自动解说或声称看见画面 |
| 英语练习 | 简单话题、短问题、主要英文，支持中文求助 | 持续引导；用户主导时跟随，不机械连续出题 |

英语学习者目前不能流利日常交流，可阅读简单英文文本。练习优先级为：聊得起来 > 语法和词汇 > 发音。每次等用户说完，先回应内容，再简短纠正最重要的一处问题；卡住时提供英文提示或中文解释，不大量讲授语法。

### 5.2 切换与回滚

- 支持“进入工作模式”“陪我练英语”等自然指令。
- 支持根据话题直接自动切换，并简短告知，不要求用户先确认。
- 建议结合上下文判断，不因一个偶然关键词频繁切换。
- 用户说“不要切换”时回滚最近一次自动切换到此前模式。
- 回滚后本次会话禁用自动切换；明确的手动切换仍有效。下一次会话重新允许自动切换。
- 会话因两分钟沉默结束时保留模式；重启恢复日常模式。
- 模式切换不创建新的个人身份，不清空当前会话，不改变勿扰状态。

### 5.3 英语总结

- 用户明确说“今天练到这里”时，简短口头总结新词与主要错误，并记录学习进度。
- 两分钟沉默、进入勿扰、关机或离开英语模式时，保存本段学习总结，不额外开口念总结。
- 保存学习进度不等同于结束当前全部聊天；进入勿扰也不自动剥夺继续主动提问的能力。
- 工程建议按已处理的练习片段记录，避免同一段因切换和会话结束被重复统计。

### 5.4 Skill 文件边界

- 模式 Skill 是设备上的文本／配置文件，描述角色、交流规则、语言、回复长度、主动行为和可用的既有能力。
- 第一代预置四种模式，支持通过本地文件上传、替换和编辑，重启程序后生效即可。
- 不开发浏览器配置、在线市场、自动安装器或复杂插件执行框架。
- 新 Skill 可以重新组织已实现的能力；不能仅靠上传文件自动获得摄像头、电脑控制等未实现能力。
- Skill 不覆盖关机、勿扰、数据处理和运动限位等基础规则。
- “个人长期档案”与“模式 Skill”分别保存：前者描述用户，后者描述机器人在某场景下怎么工作。

## 6. 本地历史与三层记忆

### 6.1 存储层次

| 层次 | 内容 | 使用与生命周期 |
| --- | --- | --- |
| 完整文字历史 | 用户识别文本、机器人回答、时间、会话标识 | 默认长期保存，用于回看和排查；不整段自动带入新会话 |
| 会话记忆 | 本轮上下文、重点、未解决的问题 | 服务当前会话；结束后退出活动上下文，但不因此删除原始文字历史 |
| 跨会话记忆 | 重要知识、待办、经历、项目近况、游戏进度、球队、学习进度、近期烦恼等 | 按相关性调用，允许低频整理与压缩 |
| 个人长期档案 | 明确偏好、长期目标、交流习惯；多次观察得到的倾向 | 高权重参考，长期保存，允许修正，不能覆盖用户当下明确要求 |

“会话结束可以忘记”仅表示不再直接把整场对话当作下一场上下文，不表示删除历史。暂不设置禁止自动沉淀的内容类别。

### 6.2 提炼、更新与读取

1. 会话结束后后台提炼重点；普通内容静默保存，不逐条询问用户。
2. 用户明确说“记住这个”时优先处理并简短确认；若保存失败，不能虚假确认成功。
3. 普通读取优先选取与当前问题相关的记忆，而不是每轮加载全部历史。
4. 个人长期档案优先参考，但当前明确要求更优先。例如平时喜欢简短回复，本次要求展开时应详细解释。
5. 一次情绪波动不能被写成固定性格。多次观察形成的倾向保留为可修正观察，不能当成用户明确自述的事实。
6. 新旧记忆冲突时需要确认；在适当时机简短询问，未获回应则保留原有已确认信息，将新信息标为待确认，不重复追问。
7. 新信息未确认不影响理解用户当前表达；待确认标记只约束长期档案覆盖。
8. 用户允许将相关本地记忆发送给云端模型；云端用于提炼的文本同样属于数据发送范围。
9. 不把机器人自己生成的猜测、未核实的搜索结果或玩笑直接固化为用户事实。建议记忆条目关联来源会话、时间和“明确表达／观察／待确认”等状态，方便排错。
10. 事项记忆仅负责记得，在相关聊天或用户询问时使用；不创建闹钟、日历或后台提醒任务。

### 6.3 压缩与维护

- 完整文字历史默认不自动删除、不进行有损压缩。
- 提炼后的记忆允许压缩，但尽量降低频率；重复明显或容量达到可配置阈值时再整理，不每次会话重写全部记忆。
- 整理不能把待确认内容变成确定事实，也不能因知识变旧就默默修改用户偏好。
- 磁盘不足时提示并记录错误，不静默删除旧历史。存储失败不得假装已完成记忆保存。
- 第一代不开发语音查询、修改、删除记忆的专门功能；保留“记住这个”的自然表达处理。
- 保存为本地可维护的数据文件；便于人工查看、备份、修改和清空，不要求提供专用管理工具或界面。

### 6.4 关机与异常恢复

- 按键关机时先保存已完成的文字历史和待提炼标记，不等待云端提炼无限完成。
- 下次启动且联网后补做未完成的提炼；处理失败保留任务状态，不能影响主对话。
- 提炼需避免重复执行造成重复记忆，建议按会话／片段标识去重。
- 异常断电时尽量保留已完成轮次，允许最后正在处理的一段不完整。
- 建议在历史中区分生成完成、实际已播报和被打断的回答，避免机器人误以为用户已经听到未播出的内容。

## 7. 表情、字幕与运动

### 7.1 外观与显示

- 风格参考《机器人总动员》的**伊娃**，以眼睛神态建立拟人感；原始 v1 的“瓦力”表述在本版修正。
- 屏幕位于头部，形态上是嵌入头部的脸部显示区域，可以没有嘴巴。
- 屏幕尺寸期望约 **8 × 8 cm**，是宽高意向，不是对角线尺寸要求；第一代允许因硬件兼容性选择其他尺寸和比例。
- 第一代不要求正式外壳，可使用支架和裸露结构；整体尽量小，但兼容性和实现可行性优先。
- 眼睛表达神态；下方一两行文字表达识别内容、回答片段和必要的设备状态。

### 7.2 表情清单与动作场景

以下场景为根据用户授权整理的初始映射；动作不是每轮必做，也不严格绑定“点头=赞同、左右转动=否定”。

| 状态／情境 | 眼睛表现 | 建议动作 |
| --- | --- | --- |
| 待机 | 自然睁眼、偶尔眨眼 | 默认保持稳定，不需机械持续活动 |
| 倾听 | 专注、柔和变化 | 可以轻微调整姿态，避免频繁动 |
| 思考／搜索 | 视线变化或思考动画 | 可小幅左右转动，不假装朝向真实物体 |
| 说话 | 随表达节奏变化 | 合适时小幅点头，不机械跟随每个词 |
| 开心／认可 | 眯眼笑 | 轻微点头 |
| 鼓励 | 温和、有精神 | 一次小幅点头 |
| 困倦 | 眼皮下垂、缓慢眨眼 | 可以保持静止，避免长时间运行电机 |
| 疑惑 | 不对称或疑问感眼睛 | 小幅左右转动；不要求新增侧倾关节 |
| 惊讶 | 眼睛放大 | 可轻微抬头，受限位约束 |
| 难过／共情 | 低垂、柔和 | 小幅低头或不动 |
| 吐槽 | 半眯眼等轻松表现 | 可短促小幅摇头，避免连续重复 |

初始表情均为本期覆盖目标，可通过少量参数化眼睛动画实现，不要求每种都有复杂独立动画素材。情绪表达应与内容相符；网络失败先通过文字和简短语音说明，不能只让眼睛“困惑”而不解释。

### 7.3 两个关节

| 关节 | 结构与作用 |
| --- | --- |
| 脖子俯仰 | 头部前后俯仰，实现点头、轻微抬头和低头 |
| 底座水平转动 | 接触桌面的底板固定，底板上方的身体和头部左右转动，实现摇头或姿态变化 |

- 不行走；不要求接触桌面的底板自己转动。
- 不要求 360° 连续旋转，建议限制角度避免缠线；实际角度、速度和承重经结构测试确定。
- 电机噪声本身不作为主要限制，但不能导致语音无法使用。
- 允许通过配置关闭全部动作，保留对话和表情。
- 检测到运动故障后停止相关动作、提示并记录日志，其他功能尽量继续运行。
- 必须有基本的运动限位、速度约束和通信失效后的停止行为；不得直接把任意模型文本当作电机指令执行。
- 上述故障检测能力依赖所选执行器和传感能力；普通无反馈舵机不能被宣称能可靠检测所有堵转，技术方案需说明可检测范围。
- 尽量使用现成双轴机构、舵机支架和加工服务，不把自行设计复杂机械作为前提。

### 7.4 表达生命周期与协调（ElectronBot review 建议）

本节细化原有眼睛、语音和动作能力，不增加自由度或新传感器。

1. **进入—保持—退出：** 表情进入时平滑变化，等待时可循环，结束后回到合适状态。可以使用参数化眼睛，不要求制作完整视频素材或移植原仓库播放器。
2. **高优先级事件可抢占：** 用户插话、明确停止和关机不必等待旧动画播完。正常退出可平滑衔接；紧急状态可缩短过渡，但不能驱动关节剧烈跳变。
3. **状态反映实际过程：** 检测到有效输入时倾听，等回答时思考，音频真正开始播放时才进入说话。请求提交成功不等于已经在说话。
4. **同轮表达一致：** 语音、字幕、眼睛与动作关联同一轮次；按回答片段触发合适的点头或开心表情，不要求逐字同步。旧轮次失效后丢弃它尚未执行的表达。
5. **本地持续响应：** 唤醒、倾听、思考、困倦等基础表情在本地实现；云端慢或断网时仍能呈现当前状态，不能把每次眨眼都交给模型决定。
6. **有限动作预设：** 采用“轻点头、轻摇头、抬头、低头、静止”等可验证预设。模型或模式可以选择表达意图，本地调度器约束频率、幅度和有效期，不接受模型生成的任意电机轨迹。
7. **避免视觉抖动：** 连续收到相同表情请求时不反复从头播放；正常情绪不因流式文本的每个小片段来回切换。过时动作直接丢弃，不排成长队。
8. **空间与可读性：** 在实际屏幕上验证眼睛主体和一两行中英字幕；20–50 cm 能看清且不遮挡眼睛，不因追求原项目屏幕规格牺牲已有字幕需求。
9. **两种延迟分别记录：** 建议从本地接受聊天按钮／检测到实验唤醒成功或有效语音活动，到倾听表情出现不超过 300 ms；该工程目标不替代“用户说完后 1–3 秒有效回答”的目标。

### 7.5 校准、反馈与上电（ElectronBot review 建议）

- 两个关节分别配置中立位置、方向、软限位、速度和动作幅度；装配或换执行器后重新验证。
- 表达预设使用相对中立位置的动作，不照搬 ElectronBot 的舵机角度、PID 或限幅数值。
- 上电先确认控制板及已配置关节可用，再在限制范围内缓慢到达中立位置；无需等待不存在的关节，不连续撞击机械边界。
- 有角度反馈的成品执行器可作为选型加分项，不新增必须自研反馈舵机的要求。
- 严格区分“下发目标”“指令已接收”“实际到位”；硬件没有位置反馈时，不把最后目标角度当作实测角度。
- 不新增手动拖动示教或复杂姿态编辑器。校准可通过开发脚本和本地配置完成。

### 7.6 结构与装配验证（ElectronBot review 建议）

- 原项目的紧凑结构不能直接同比放大来容纳约 8×8 cm 的屏幕。先测量屏幕、支架、线材形成的头部重量与重心，再确定颈部执行器。
- 主控、散热器和较重部件尽量位于固定底板或较低位置，减少颈部及旋转部分负载；最终布局以走线和结构验证为准。
- 对俯仰和左右旋转检查线材长度、弯折余量、应力释放和限位，避免电源／显示线随动作拉扯接插件。
- 在最大规划动作范围内验证底座不倾倒、结构不碰撞、线材不绷紧；验证电机启动时主控不重启、音频不持续受干扰。
- 裸露结构也要有明确脸部朝向、稳定固定、基本理线和可拆装维护；不要求增加美观外壳。
- 不以原项目历史打印费用作为本期价格依据，实际支架、加工、执行器和电源配件统一进入 BOM。

## 8. 系统组成与可扩展性

### 8.1 建议组成

本节保留已确认的自建 B 路线基线。新增成品 A 路线的 MCU 或双设备部署需要按第 18 节评估，不代表已替换 Linux 部署和原验收条件。

| 组件 | 责任 |
| --- | --- |
| Linux 主控 | 聊天触发、可选实验唤醒、音频流、云端 API 接入、会话状态、模式、搜索调度、记忆、屏幕和日志 |
| 小控制板 | 电机指令执行、按键检测、状态反馈；配合电源控制电路实现主控关机后再开机 |
| 显示与音频 | 眼睛／简短字幕显示、近距离收音、外放；验证自身播放时的收音与打断 |
| 本地存储 | 历史、三层记忆、Skill、配置、日志、待处理任务 |
| 云端服务 | 语音识别、对话推理、语音输出、搜索及必要的记忆提炼 |

Ubuntu 优先；若所选硬件使用其他 Linux 更可靠，可接受。编程语言、控制板型号和通信协议留待技术方案确定，不强制全 Java，也不要求引入 ROS 等完整机器人框架。

### 8.2 云端方案

- 优先验证豆包／火山引擎，允许采用其他在中国普通家庭网络下可直接访问的服务。
- 优先减少接入复杂度；可以评估端到端实时语音，也可以采用语音识别、文本模型、语音合成的分模块组合。
- 不能仅因“端到端”就假定满足所有需求，需验证：打断、识别文本、输出文本、本地记忆注入、模式切换、异步搜索和事件控制。
- 允许多个 API 凭证及单独文本模型用于记忆提炼；“一个 API Key 完成全部功能”不是硬性要求。
- 设备直接调用供应商，不要求租用云服务器。
- 不把待机的全部环境声音或全部历史持续发送到云端；在必要时发送相关数据。
- 端到端语音服务及部分新语音接口的鉴权形式不同；按最终采用接口的官方文档配置，不能默认普通文本模型的 Key 能通用。相关官方依据见第 15 节。

### 8.3 摄像头与 NVIDIA 扩展

- 第一代预留可用的摄像头连接路径，例如可用于 USB 摄像头的端口；具体 CSI 接口是否保留由选型决定。
- 不安装、不实现视觉；“预留”应检查端口、供电、安装空间和软件模块边界，不只写一句支持。
- 方案 B-J：第一代直接使用 Jetson 类主控，自带 NVIDIA GPU，为未来视觉等功能准备。
- 方案 B-L：第一代使用普通 Linux 主控，未来增加 Jetson 类独立计算板，通过局域网等本地通信协作；未来计算板、供电和散热另行预算。
- 方案 B-L 是增加一台计算节点，不是承诺把 Jetson 作为普通 PCIe 独立显卡插入现有主控；也不要求实现多机 GPU 共享。
- 本期在方案 B-L 下预留有线网络连接能力及软件模块接口，不开发尚未购买的 Jetson 节点服务。
- 云端聊天不因选了 Jetson 就自动改成本地大模型，第一代仍采用云端主要智能能力。

### 8.4 表达调度与外设隔离（ElectronBot review 建议）

建议将“对话与记忆”“本地表达调度”“显示／音频／运动驱动”分层。对话侧产生语义和状态，表达调度选择有限预设、管理取消和过期，驱动层执行经过约束的操作。

- 语音接收和打断、屏幕刷新、关节通信不互相无限等待。一个执行器失联不得使整机启动、聊天或关机流程卡死。
- 每条外设通信流程具备总等待期限、取消路径和明确错误返回；仅设置每次底层调用的超时而无界重试仍不合格。
- 运动控制板建议具备就绪确认、心跳和失联处理；恢复连接时重新确认状态，丢弃旧动作，不补播积压指令。
- 失联后的保持、减速和断力策略按实际结构确定；不能一律断力导致头部下坠。正常退出、通信故障与主控关机分别验证。
- 优先让 Linux 主控直接驱动兼容屏幕，小控制板承担运动与按键等职责；不强制复制 ElectronBot 的 USB 图像推帧与 I2C 舵机链路。
- 若选用 MCU 驱动屏幕，也需保留独立显示降级和本地状态反馈，不能仅因复用原代码就使其与所有关节绑定。
- 成品日常运行不依赖用户电脑上的 Unity、Windows DLL 或常驻控制程序；开发阶段使用电脑调试不影响这一要求。

## 10. 配置、日志与异常处理

### 10.1 本地配置

至少覆盖：服务提供商及凭证引用、模型与音色、音量和语速、模式 Skill 路径、15–20 分钟主动间隔、30 秒邀请窗口、两分钟会话超时、10 分钟延长等待、字幕与困倦配置、运动开关及设备参数。

第一代采用本地配置文件和日志文件，允许使用系统现有方式配置 Wi-Fi、连接和维护。无需另做专用 CLI 产品、管理网页、语音音量命令或备份界面。配置错误需有明确日志，不可悄悄使用错误的凭证或空 Skill。

凭证与历史分开保存，日志不得输出完整 API Key 或鉴权头；这是本地诊断实现的基本约束，不增加用户审批步骤。

### 10.2 日志

建议记录以下排错信息：

- 会话、轮次、模式、唤醒和状态切换时间。
- 用户语音结束、识别完成、首段有效回答播放的时间，用于区分网络、判停和合成延迟。
- 插话开始、旧音频停止、新输入处理的时间。
- 搜索请求、超时、结果过期或失效、错误类型。
- 记忆提炼任务、保存失败、待确认冲突、恢复执行情况。
- 控制板连接、运动指令失败、关机请求及恢复情况。
- 可取得的云端用量信息；无法取得的字段不能伪造。

完整文字历史与诊断日志分开管理；诊断日志可轮转，不能借日志轮转删除用户要求长期保留的文字历史。原始录音不进入默认日志。

### 10.3 异常行为

| 异常 | 用户可见行为 | 恢复要求 |
| --- | --- | --- |
| 断网 | 本地眼睛与错误文字继续，必要时简短提示；不假装仍在回答 | 网络恢复后服务可重新使用，无需手动重启；不补播过时回答 |
| 云端超时／不可用 | 结束无期限等待，简短说明暂不可用 | 有限重试与恢复，不反复播报同一句错误 |
| 凭证无效／额度错误 | 可理解的服务不可用提示，本地日志给出具体原因 | 修正配置后可恢复；不能靠无尽重试解决配置错误 |
| 连续识别失败 | 两次后提示并回待机 | 用户下次按聊天按钮可重新开始 |
| 搜索超过 20 秒 | 说明未查到，必要时给明确标注的不确定解释 | 不再阻塞当前聊天，不猜实时比分 |
| 记忆提炼失败 | 正常对话尽量继续；明确记住请求失败时不能谎报成功 | 保留文字和任务，之后补做 |
| 磁盘空间不足 | 显示保存异常，记录能记录的诊断信息 | 不静默删历史，人工维护后恢复 |
| 关节／控制板故障 | 停止相关运动，显示简短提示 | 语音与表情尽量继续；故障范围以实际可检测能力为准 |
| 外设未就绪／连接中断（review 建议） | 报告该项能力不可用，其他已就绪能力继续 | 总期限内退出等待；恢复后重新确认状态，不执行过期动作 |
| 意外断电 | 下次启动检查未完成任务 | 已完成轮次尽量保留，最后未完成片段允许不完整 |

离线不要求聊天或识别控制口令。系统关机、按键和本地显示不能依赖云端成功。

## 11. 需求优先级与交付顺序

以下为开发顺序，不表示可以从第一代最终范围中无声删去功能。

| 顺序 | 交付内容 | 完成证据 |
| --- | --- | --- |
| 第一闭环 | 听懂一句问题并通过扬声器回答 | 实机完成一轮对话 |
| 自然交流 | 按钮开始聊天、连续交流、打断、错误提示、基础字幕 | 10 轮交流与打断记录 |
| 可长期使用 | 历史、记忆提炼、模式 Skill、勿扰、主动搭话 | 跨会话和状态边界用例通过 |
| 实体体验 | 两轴结构、眼睛、情境动作、单按钮电源流程 | 实机演示与电源流程验证 |
| 完整交付 | 搜索、英语练习、恢复能力、预算核对、持续运行 | 主观体验回访及第 12 节验收记录 |

高风险事项应前置并行验证，不必等到对应功能正式开发阶段：音频回声与打断、按钮开始连续会话、云端服务可用性、两次按键启动的电源结构、整机 BOM。

**ElectronBot review 建议：** 第 1–2 周增加最小表达样机，用本地模拟事件演示“唤醒—倾听—思考—说话—被打断—回到倾听”；已具备硬件时加入单关节点头。它用于提前检验实体感，不要求此时完成记忆或云端整链路。

提供轻量开发自检脚本／入口，分别测试屏幕、收音外放、单关节、双关节和按键，再做联调；可缺少部分外设运行，不新增用户管理界面或离线聊天能力。

## 12. 验收方案

用户授权本版拟定量化验收指标；以下是工程建议基线，尚无实测结论。用户可结合体验调整指标；任何调整需更新记录，不在失败后悄悄改变测试口径。

### 12.1 环境与口径

- 安静书房，距离 20–50 cm，正常说话音量；电脑游戏／比赛使用耳机，无外放背景声。
- 使用拟交付硬件、真实家庭 Wi-Fi、真实云端服务；记录测试日期、配置与网络异常。
- 至少覆盖 20 cm 与 50 cm，不只在最有利距离测试。
- 普通回答延迟从用户实际说完到首段有实质内容的可听回答；不将提示音、“好的”“我查一下”算作有效答案，也不把语音判停等待从延迟中剔除。
- 主观体验、测试失败和服务异常都记录。明显云端故障可单列复测，但不得从报告中抹去失败样本。
- 定时规则可用短时配置辅助测试，但两分钟、10 分钟、15–20 分钟与 30 秒各至少做一次真实时长验证。

### 12.2 功能与体验验收表

| 编号 | 项目 | 建议验收方法与目标 |
| --- | --- | --- |
| AC-01 | 单按钮流程 | 完成至少 5 次完整循环；每次关机后先按键启动到黑屏未启用，再按键启用；无长按、无二次确认 |

| AC-16 | 表情与动作 | 表情清单均可触发；点头与左右转动可用；动作适时、不每句必动；字幕不遮掉整个眼睛区域 |
| AC-17 | 故障降级 | 通过受控断开控制通信等方式测试可检测故障；停止相关运动，语音尽量继续；关闭动作配置生效 |

## 18. Stack-chan 与硬件路线变更（2026-10-24）

### 18.1 已授权的评估范围

用户希望比较成品与自建两条路线，以降低硬件成本和装配工作，并参考社区能力。评估对象明确为官方 **M5StackChan K151**；“1000 元内”是已撤回确定性的初步估计，不是已核实价格或新的硬上限。用户接受“成品 + 本地专用主机”作为备选，尚未选定该方案。

| 路线 | 定义 | 成本与收益 | 尚需解决 |
| --- | --- | --- | --- |
| A1 成品单机 | 在 K151 上自主开发固件并连接云服务 | 机械和布线已集成，硬件费用以真实到手价加缺件计 | MCU 部署、按钮会话、打断、存储、Skill、按钮与扩展 |
| A2 成品 + 本地主机 | K151 负责交互，专用 Linux 主机负责智能调度与持久化 | 初步预算占位 2300–3600 元，非采购报价；减少机械自制 | 自主音频传输、终端回声与停播、双设备电源、主机空间 |
| B 自建 | 自购主控、屏幕、音频、控制板、两轴并集成 | 整机预算仍不超过 5000 元；自主选择接口、尺寸与布置 | 装配、供电、音频、散热、后续外壳预留与总体工作量 |

B 内部分为 B-L（普通 Linux + 后续外接 Jetson 节点）和 B-J（本期直接 Jetson），对应原 A/C；本次只是消除名称冲突，不改变原 NVIDIA 偏好与预算规则。

### 18.2 自主开发与需求差异

官方社区提供 K151 对应固件的源码构建/刷写路径，官方亦提供固件与 Arduino BSP，支持自主开发这一方向；**尚未证明任一现成固件能完整满足 Jarvis**。依据与详细比较见 [Stack-chan 评估](stackchan-review.md)。

确定成品路线前，必须逐项核对：

- 按钮开始连续聊天、结束后再次开始，以及聊天键与电源键的区分；五短句唤醒已延期到 V2，不再是 A1/A2/B 的 V1 准入门槛。
- 全双工收放音、打断后清空播放队列、旧输出失效；有双麦克风不等于回声消除达标。
- 完整文字历史、三层记忆、提炼任务恢复与四模式 Skill。社区 MOD 不是这些功能的替代品。
- 成品 2 英寸屏幕的字幕可读性与原尺寸偏好；现有“必要时服从硬件”不免除 20–50 cm 实际体验检查。
- 成品长按关机与原单次短按保存关机的差异；A2 还须明确一个按钮控制两台设备的方法。
- A1 的 MCU 平台与 Linux 文件维护要求的差异；A2 的专用主机不得隐含依赖日常 Mac 常开或额外租服务器。
- 成品自带摄像头和电池：建议允许物理存在，V1 不启用视觉、不新增电池能力验收；若选择 A，明确确认其与第 8.3 节“不安装”措辞的变更。
- 摄像头、NVIDIA 与有线连接预留分别核对；成品可连 Wi-Fi 不代表原全部扩展条件已满足。

以上是待决策差异清单，未获用户明确取舍前不删除或放宽原功能与验收；任一路线不能以开源、可刷机或能聊天作为全部达标的替代证据。

### 18.3 自建路线的复用与外壳预留

允许参考或复用许可兼容、硬件匹配的社区表情/动作能力分层、驱动、自检和结构资料。Jarvis 不要求每个驱动和支架从零开发；两轴标定、承重与供电仍由自己的实机验证。

为 V2 外壳提前记录各部件外形、重量、安装孔、接口朝向、散热净空和运动范围；选型时形成简单布局图，优先固定底座承载重部件，减少头部负载，保留可拆连接与走线空间。V1 不增加精美外壳交付要求。更强可扩展性不意味着任意升级都不需调整结构。

### 18.4 推进与验收

- 硬件路线评估为 P1 独立任务，Mac 语音接入、轮次取消、文字与记忆接口继续推进；不能等待买到成品才开始语音验证。
- W2 检查点仍为 2026-11-05，输出 A1/A2/B 的证据、完整成本和需求差异；无法完成硬件实测时明确剩余条件，不假定通过。
- 路线确认前不进行采购或烧录。需要时将具体商品、总额、验证目标和可恢复方式提交用户选择。
- AC-02、AC-05、AC-14、AC-20、AC-24 等现有验收覆盖按钮会话、打断、记忆、预算扩展和失联；A2 须包含本地链路断开/恢复与旧音频不重播场景。数字目标仍依 PRD 的工程目标规则执行。
- T0 和三个月目标日不变；若验证显示新增集成工作影响进度，列出证据与取舍后再调整，不预先承诺节省工期。
