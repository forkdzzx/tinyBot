## 当前选择

先在 Mac 上验证体验与接口，实际部署根据 A1（K151 MCU）、A2（K151 + Linux 主机）或 B（自建）证据选择；尚未替换原 Linux 基线。优先评估豆包端到端语音；如果文本获取、记忆注入或搜索工具无法满足需求，再评估 ASR + 文本模型 + TTS。不为尚未验证的 SDK 预设接口，也不先造完整平台。

表达原型以 Node 标准库启动本地页面，纯事件状态转换与显示分开，验证模拟唤醒、表情及轮次失效。另有真实语音原型，通过 Node WebSocket 代理接入 Seeduplex，浏览器负责收音和 PCM 播放，已实现停止播放和清空队列；两者尚未集成为完整机器人状态机。

## 唤醒候选

优先评估 sherpa-onnx 的开放词表关键词检测。官方文档支持自定义词表、按模型分词，并提供每词阈值与增强分数；这符合五短句需求，但不证明 Jarvis 名称或用户口音能稳定识别。[官方文档](https://k2-fsa.github.io/sherpa/onnx/kws/index.html)

需要特别验证三件事：

1. `Jarvis!` 是两条长句的前缀：单词先触发后，不能把剩余唤醒短句误当作业务问题；必须保留首个实际问题。前缀处理策略以真实音频测试确定。
2. 对比英语原句自然连读与用户实际发音，不按展示标点要求停顿；分词输出须来自所选模型资源，不凭空手写 token。
3. 五条同时开启，既测每条命中，也测普通谈论名字的误触发。不得以“Jarvis”一词命中来冒充整条长句已独立验证。

模型下载、依赖安装和麦克风测试尚未执行。模型许可证、平台包、体积和真实资源占用均进入选型证据。此候选主要用于 Mac/Linux 验证，不承诺可直接运行于 K151 的 ESP32-S3；A1 需另行验证嵌入式唤醒引擎，A2 需验证本地音频上送链路。

## 语音验证记录格式

每次记录：服务/模型版本、音色、网络、麦克风、场景、用户实际说完时间、首段有效声音时间、插话起点、声音停止时间、是否保留双方文字、是否有旧回复冒出、调用用量。首次用 10 轮中文与一段基础英语练习发现问题，不将小样本当作最终验收。

服务文档有能力不等于实测通过。后续至少覆盖普通问答、较长停顿、生成中插话、播报中插话、搜索返回前换题、暂时断网，以及会话结束后停止上传声音。

## 决策门槛

- 端到端路线必须能获取可用文字、携带相关记忆、控制对话风格并容纳搜索事件，不能仅用一次流畅对话选定。
- 主控必须支持显示、音频、唤醒和电源流程；Jetson 是否进入本期由完整 5000 元 BOM 决定。
- 原型只验证模块责任与体验；勿扰、主动搭话、长时等待、历史持久化和真实断网恢复均未在当前页面实现。
